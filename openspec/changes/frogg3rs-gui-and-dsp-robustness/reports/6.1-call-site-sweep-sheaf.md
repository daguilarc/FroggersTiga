## Triage: MISSING rows

**`synth::ScopeWriter::RecordStart` (`app/dsp/Vco.hpp:47-52`).** Already
confirmed by the task brief; re-verified here. `WavetableVco::Process`
(`DspOscillators.hpp:154-159`) calls `RecordStart(0, markerOffset)` at every
detected cycle-top (`m_top`), so Sheaf's reference oscillator writes a cycle
marker into the scope's ring buffer every period. `app/dsp/Vco.hpp`'s
`Process()` writes samples but never calls `RecordStart`, and the header's
own comment (`:47-52`) states this was a deliberate, flagged omission ("no
marker/cycle-alignment requirement" for packet 7's tests). Consequence,
verified by reading `ScopeReader`/`BuildScopeWaveformCommands` (not just the
writer side): `synth::ui::ScopeVisualizer` was constructed with
`drawMarkers=true` (`FroggersAppCore.hpp:122`), and the marker-draw branch in
`PortableUIBuilders.hpp:210-219` only emits the playhead-highlight ellipse
when `ScopeMarkerBounds` derives a valid marker position from
`ScopeWriter::LatestStart`/`PreviousStart` — both of which stay at their
constructed defaults (`0.0`/zeroed `startMarkers_`) forever, since nothing
ever calls `RecordStart`. The oscilloscope waveform itself still draws
correctly (Write/AdvanceIndex/Publish are all present and correct), but the
x-axis is not phase-aligned to the waveform's own cycle — each refresh shows
whatever raw window of the ring buffer currently sits at the read cursor, not
a cycle-locked slice, and the intended cycle-marker dot never appears. This
is a live but purely cosmetic defect (the scope panels are not blank — that
was the *other*, already-fixed `AdvanceIndex` bug — this one is "the
waveform doesn't visually settle/sync between refreshes").

**`synth::GangedRandomLfoProcessor<1>::SetVoiceColor`
(`app/FroggersModulation.hpp`, `gangedRandomLfo6_` member).** Sheaf's own
`StandardModulators<VoiceCount>::Init` calls
`randomProcessors_[random].SetVoiceColor(voice, config_.randomVoiceColors[voice])`
for every one of its `GangedRandomLfoProcessor` instances
(`StandardModulators.hpp:128`) before registering them as modulation sources
with matching `sourceColor` metadata. Froggers's `gangedRandomLfo6_` (also a
`GangedRandomLfoProcessor<1>`, registered as "Random S&H 6" with
`sourceColor = LaneColor(5)`, `FroggersModulation.hpp:517`) never calls
`SetVoiceColor`. Consequence, verified by reading
`GangedRandomLfoAtomicColor`'s default (`DspRandomLfo.hpp`:
`std::atomic<std::uint32_t> value{Color::Grey.Packed()}`, i.e.
`Color::Rgb(128,128,128)`, `Color.hpp:185`) and
`BuildGangedRandomLfoCommands` (`GangedRandomLfoVisualizer.hpp:212,233,242`,
which draws the polyline/dash/dot in `voice.color`): the "Random S&H 6"
visualizer's line and playhead dot render in flat mid-gray instead of the
lane's intended magenta-pink hue (`LaneColor(5)` = HSV(330°,0.65,0.95)) used
everywhere else that source is represented (its `sourceColor` metadata, its
modulator-affecting indicator dots on other encoders, etc.). This is a real,
narrowly-scoped color-consistency bug, not a missing-animation bug — the
data flow (`Prepare`/`Process`/`Output`/`PublishUiState`) is fully wired, so
the "dice roll" motion itself is present; only its color is wrong.

**`synth::ParameterGroup::ConfigureProcessingTiming`
(`app/FroggersAppCore.hpp` / `FroggersParameters.hpp`).** Braid4 calls this
once per group, every `PrepareToPlay(sampleRate, blockSize)`
(`Braid4Core.hpp:207-220`), converting the class's 48kHz-referenced defaults
(`kDefaultProcessLiteAlpha`, `kDefaultTargetComputeIntervalSamples`,
`kDefaultUiDisplayCenterAlpha`, `kDefaultUiDisplaySpreadAlpha`,
`ParameterModulation.hpp:170-174`) to the app's actual (possibly oversampled,
for Braid4) processing rate via `ConvertOnePoleAlpha`/`ConvertSampleInterval`.
Froggers's `FroggersAppCore::PrepareToPlay` (`FroggersAppCore.hpp:218-285`)
never calls it for `parameters_.Group()`. Consequence, verified by reading
`Parameter::ProcessLitePhase1`/`ProcessLitePhase2`
(`ParameterModulation.cpp:1439-1479`) and `ProcessSamplePhase1`
(`:1486-1488`): `config_.processLiteAlpha` sets the per-sample one-pole
smoothing rate for scene-blend/modulation-depth/knob glide,
`config_.uiDisplayCenterAlpha`/`uiDisplaySpreadAlpha` set the encoder ring's
own display-slew rate, and `config_.targetComputeIntervalSamples` gates how
often (in samples) the expensive `Compute()` re-derives each parameter's
target value. Because Froggers's `RuntimeConfig::preferredSampleRate` is
48000.0 (`FroggersAppCore.hpp:156`) — the same reference rate the unconverted
defaults are tuned for — this is silent as long as the host actually
negotiates 48kHz. If the host negotiates a different rate (any other
device-supported rate; `PrepareToPlay`'s own comment,
`FroggersAppCore.hpp:239-266`, documents that real sessions do get
renegotiated, e.g. block-size changes mid-session), every one of these four
timing constants stays wrong-for-rate: knob/modulation-depth glide and the
encoder-ring display slew run measurably faster or slower (in real seconds)
than intended, proportional to how far the negotiated rate is from 48kHz,
and `Compute()` fires more or less often than the intended ~3kHz cadence.
This is a genuine, previously-undocumented dropped call site matching the
task's exact defect signature, distinct from the two ScopeWriter issues.

## The two specific questions

**1. Is `synth_froggers::RandomShVisualizer` ever attached to an encoder cell
in production?** The type named in the task brief does not exist under that
name — `app/FroggersRandomShVisualizer.hpp` defines
`synth_froggers::RandomShLaneVisualizer` (not `RandomShVisualizer`). That
class **is** attached in production, for all five X-style lanes: each of the
five `RandomShLaneVisualizer` instances is passed as the `visualizer` field
of its `ModulatorMetadata` at `FroggersModulation.hpp:504-513`
(`group_->SetModulationSource(i, src, {..., randomShLaneVisualizers[i], ...})`).
The sixth Random S&H source uses a different (Sheaf-native) visualizer type,
`synth::ui::GangedRandomLfoVisualizer<1>`, also attached at
`FroggersModulation.hpp:517`. Both attachment sites feed Sheaf's own,
entirely automatic plumbing: `Bank::HandlePress` →
`Parameter::EnsureModulationDepth`/`ModulationDepthConfig`
(`ParameterModulation.cpp:1859-1875`, `.visualizer = modulator.visualizer`)
materializes a local depth `Parameter` carrying that visualizer, and
`synth::Engine`'s automatic per-block `ParameterManager::PopulateUIState` →
`BankSlot::PopulateUIState` → `Parameter::PopulateUIState`
(`ParameterModulation.cpp:2984-3000`, `:1254-1269`) writes it into
`BankSlot::UIState.cells[ix].visualizer` — the exact pointer
`FroggersUiSurface.hpp:648`/`Braid4UI.hpp:76` read. `PublishUiState()`
(`FroggersModulation.hpp:430-435`) is called every block from
`FroggersAppCore::ProcessBlock` (`:494`) and does populate both the five
lanes' `dsp::RandomShLane::UiState` and `gangedRandomLfo6_`'s own UiState.
**Contrary to the operator's suspicion cited in the task brief, this
plumbing is fully wired and verified end-to-end; no dropped call site was
found for it.** The one verified, narrowly-scoped defect touching source #6
is the `SetVoiceColor` omission above (wrong color, not missing animation).
If the "dice roll" animation is genuinely absent for the operator, the cause
is not in this call-site sweep's scope (candidates outside this survey: the
drill-in view never actually being entered for that source, a rendering-
backend issue, or something specific to the live build not reflected in this
source tree) — flagged rather than guessed at further.

**2. Does anything in production write `slotState.cells[ix].visualizer` at
all?** Yes, but not `app/` code directly — it is Sheaf's own
`Parameter::PopulateUIState` (`ParameterModulation.cpp:1269`,
`state.visualizer.store(config_.visualizer, ...)`), invoked automatically,
once per (throttled) block, for whichever `Parameter*` currently occupies
each bank-slot cell (`BankSlot::PopulateUIState`,
`ParameterModulation.cpp:2984-3000`), itself invoked automatically by
`synth::Engine`'s own UI-publish path (`Engine.hpp:412`,
`manager_.PopulateUIState(*uiState_)`). App code's only responsibility is to
register the correct `.visualizer` at the two config sites Sheaf exposes:
- **`ParameterConfig::visualizer`** (per ordinary/top-level parameter,
  `ParameterModulation.cpp:1269`) — attached for: Filter bank's Peak
  parameters (paramIx 1-3) and Comb parameters (paramIx 4-6), both via
  `synth_froggers::TransferFunctionVisualizer` (`FroggersParameters.hpp:316-329`).
  Never attached (legitimately — no visualizer type exists for these) for
  every other top-level page parameter, Crispy, or Crunchy.
- **`ModulatorMetadata::visualizer`** (per modulation source, consumed via
  `ModulationDepthConfig` when a depth parameter is materialized,
  `ParameterModulation.cpp:1872`) — attached for modulation slots 0-5
  (Random S&H 1-6: `RandomShLaneVisualizer` x5 +
  `GangedRandomLfoVisualizer<1>` x1) and slot 12 (Noise:
  `NoiseWaveformVisualizer`). **Never attached** (explicit `nullptr` at
  registration) for slots 6-8 (VCO1-3 Audio), 9-11 (VCO1-3 EF), 13-14
  (External Audio + EF) — `FroggersModulation.hpp:522-549,565-571`. This
  matches Braid4's own convention exactly: its four modulation sources
  (Audio XY, LFO XY, Matrix, LFO Matrix, `Braid4Core.hpp:367-402`) also
  register with no `.visualizer` field set (defaults to `nullptr`), so a raw
  audio/LFO/matrix modulation source having no dedicated visualizer is the
  established Sheaf pattern, not an app-specific gap.
