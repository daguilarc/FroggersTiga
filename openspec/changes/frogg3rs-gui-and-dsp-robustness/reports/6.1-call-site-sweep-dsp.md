## Triage of non-`OK` rows

**`StereoDelay::ClearBuffers` (`dsp/Delay.hpp:77`) — NEVER-CALLED.** The
only call site anywhere in the tree is `FroggersDspParityTests.cpp:1205`
(`delay.ClearBuffers();`), a hand-constructed test object — exactly the
blind-spot shape this sweep was built to catch. Read against what actually
runs: `FroggersAppCore.hpp:237` calls `delay_.SetSampleRate(sampleRate_)`
exactly once, from `PrepareToPlay`, before any `Process()` call.
`StereoDelay::SetSampleRate` (`dsp/Delay.hpp:87-100`) itself performs
`lineL.assign(capacity, 0.0f)`, `lineR.assign(capacity, 0.0f)`,
`writePos = 0`, and `lfoPhase = 0.0f` — i.e. every piece of state
`ClearBuffers` also resets, with one exception: `ClearBuffers` additionally
sets `lastWet = {}` (`dsp/Delay.hpp:83`), which `SetSampleRate` does not
touch. But `lastWet` is a `DelayWetPair` member that default-constructs to
`{0.0f, 0.0f}` (`dsp/Delay.hpp:65-67`), and `SetSampleRate` runs before the
member has ever been written by `Process()` — so at the one call site that
exists, `lastWet` is already sitting at the exact value `ClearBuffers` would
have set it to. There is no code path in production that constructs a
`StereoDelay`, calls `Process()` one or more times, and then needs a
buffer-clearing reset without a paired `SetSampleRate` call (no "panic
reset" or transport-stop handler touches `delay_` at all — confirmed by
grep, `delay_` has exactly three call sites in `FroggersAppCore.hpp`:
`SetSampleRate`, `Process`, `ToReverbMono`). Verdict: **benign, not a live
defect** — this is the same shape as the confirmed historical bug class
(a configuration method with no production call site), but unlike
`ResonantBump`'s setters, the one production call site that does exist
(`SetSampleRate`) happens to perform every state reset `ClearBuffers` would
have performed, at the only point in the object's lifecycle where it would
matter. Worth flagging to a human because "the safety net is a coincidence
of call order, not a guarantee" is exactly the kind of latent fragility this
defect class produces — a future refactor that reorders `PrepareToPlay` or
adds a mid-session panic-reset could reintroduce a real gap — but as the
code stands today it is not causing incorrect behavior.

## Notes on rows resolved via internal (dsp-to-dsp) call chains

Several methods have no *direct* call site in the app-tier files
(`FroggersAppCore.hpp` etc.) but are reached exclusively through another
`app/dsp/*.hpp` unit calling them — which the task brief explicitly counts
as production ("one DSP unit calling another counts as production"). These
are not flagged as `TEST-ONLY`/`NEVER-CALLED` because the calling unit
itself has a confirmed production call site, so the chain is live:
`ResonantBump::UpdateCoefficients` (called only from `ResonantBump`'s own
ctor/setters), `PolynomialDrive::Process`/`SampleRateReducer::Process`/
`DigitalReorganizer::Process`/`Oversampler2x::Process` (called only from
`FrogBlock::Process`), `Comb::Process`/`PureDelay::Process`/
`ResonantBump::Process` (called only from `FilterFxChain::Process`),
`Vco::StepPmLfo` (called only from `Vco::Process`), `RGen`'s four methods
(called only from `RandomShLane`'s ctor/`Increment`), and
`VcoAdsrState::setSampleRate`/`apply` (called only from `VcoAdsrState::init`
and `MixOscVoices` respectively). Each of those outer callers was itself
traced to a direct app-tier call site, so the whole chain is confirmed live,
not assumed.

One asymmetry worth noting for a human, though it does not change the
verdict: `ResonantBump::PopulateUIState` is called for the `peak` instance
(`FroggersAppCore.hpp:492`) but not for `scoopNotch` — `filterChain_` has no
`scoopUiState_`/`scoopVisualizer_` member, only `peakUiState_`/
`peakVisualizer_` and `combUiState_`/`combVisualizer_`
(`FroggersAppCore.hpp:793-794,800-801`). Since the method itself has a
confirmed production call site (on a different instance of the same type),
this is `OK` per the method-level sweep this task specifies, not a
per-instance one — but it means the scoop notch's transfer function is not
currently visualizable, which may or may not be intentional design (design
D10/task 9.1 only cites `peak`/`comb` gaining `UIState`, so this reads as
deliberate scope, not a dropped call site).

Also worth noting: `FroggersAppCore.hpp:667-678` contains an explicit
in-code comment documenting that `ResonantBump scoopNotch`'s three setters
(`SetFreq`/`SetWidth`/`SetHeight`) were previously dropped from production
and have since been restored ("restored 2026-07-27") — this is the exact
defect class described in this task's background, already fixed in the
code as it stands today. This sweep re-confirms all three setters are
currently wired for both `peak` and `scoopNotch`
(`FroggersAppCore.hpp:664-666,680-683`).
