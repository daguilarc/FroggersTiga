## Context

Froggers exists today as three products sharing `src/core/`: the **Daisy field firmware** (`src/FroggersTiga/`), the **v1 desktop** (`desktop/`), and **desktop-v2** (`desktop-v2/`, JUCE + VST). The archived `desktop-v2-sheaf-runtime-harmonization` change attempted to converge desktop-v2 onto Sheaf in place. Its 2026-07-25 omni preflight audit found that (a) the remaining migration was largely deletion of a bespoke host layer, and (b) nearly every unresolved complication in the plan — label forking, host-kind flag-gating, "retain but neutralize" parameters, "do not touch shared infra" — traced to desktop-v2 sharing `src/core/` with Daisy.

This change starts a **new app** instead: Sheaf's classes, Froggers' topology, its own copy of the DSP, and no shared file with Daisy/v1.

Sheaf is consumed as a **git submodule** at `External/Sheaf` (`https://github.com/jvictor0/Sheaf.git`), pinned at `1940ddcb` (superseding the earlier pin `dafa54b6`), alongside the pre-existing `External/theallelectricsmartgrid` submodule (`.gitmodules`). `1940ddcb` ("feat(sheaf-patch): allow build-time injection of an out-of-tree app") is the commit that adds Sheaf's out-of-tree app-registration hook to `sheaf-patch` (see D1a) — the 4-commit range advancing to it touches only `apps/sheaf-patch/Main.cpp` and `apps/sheaf-patch/Makefile` under `projects/synth`; everything else in the range is `projects/agents/`, `projects/xagent/`, and openspec docs, none of which this app compiles. This supersedes the archived change's D1 ("vendor in-tree, no submodule") by operator instruction 2026-07-25.

**Reference app: `braid-4`.** It is the canonical Sheaf app shape and, per operator, **the guiding light for visualizers** — including how knob/encoder rendering reflects post-processed parameter values.

## Objective (OpenSpec §2)

Ship Froggers as a Sheaf-native `SynthApplication` that runs under Sheaf **Runtime** (desktop, via the `sheaf-patch` launcher) and the Sheaf **browser/patcher** host, using Sheaf's parameter/bank/modulator/visualizer facilities with Froggers' DSP topology and value scaling — monophonic, one 16-slot bank per Froggers page (Crispy fixed at slot index 14, Crunchy at slot index 15, per-bank colors), a fixed 15-source modulation slate with drill-in permitted to two levels, fuegoization re-homed onto Braid's parameter-filtering seam, VCO/Marbles/filter visualizers, master-clock-driven Marbles — publish it as a Sheaf browser package this repo hosts for registry listing, and make that **same browser build the public Froggers website**, superseding the legacy `web/`+`wasm/` site without modifying it.

**Slot indices in this document are 0-based**, matching Sheaf's physical encoder ids (`apps/braid-4/Braid4Core.hpp:163-183` builds encoders `0..15`). A 16-slot bank therefore has slots `0..15`; Crispy is index **14** and Crunchy index **15**. Where prose says "the fifteenth slot" it means index 14. This matters beyond presentation: D6 defines each parameter's fuego row identity as its 0-based slot index, and `Fuegoize`'s shift is `sh = 1 + (row % (mask+1))`, so the base changes the sound.

## Decisions

### D1 — Sheaf as a git submodule at `External/Sheaf`
**Choice:** consume Sheaf via submodule (`https://github.com/jvictor0/Sheaf.git`, pinned `1940ddcb`, superseding `dafa54b6`), matching the existing `External/theallelectricsmartgrid` convention.
**Why:** operator instruction 2026-07-25; keeps a single upstream-tracked copy with an explicit pin. The bump to `1940ddcb` picks up Sheaf's out-of-tree app-registration hook (D1a) — the 4-commit range advancing the pin touches only two files under `projects/synth` (`apps/sheaf-patch/Main.cpp`, `apps/sheaf-patch/Makefile`); the rest of the range is `projects/agents/`, `projects/xagent/`, and openspec docs, none of which this app compiles.
**Supersedes:** archived D1 ("vendor slices in-tree; no submodule") and the `froggers-v2-sheaf-runtime` local-ownership rule, which were written for the desktop-v2 tree.
**Consequence:** the vendored slice at `desktop-v2/External/Sheaf` (`c1810393`) is now a *second* copy. It stays only because desktop-v2 is frozen; the new app must never reference it. If desktop-v2 is later retired, that copy goes with it.

**AMENDMENT (operator-approved 2026-07-27): Sheaf is now a permanent fork, not a pristine upstream pin.** `PortableJuceBackend.hpp`'s `RetainedDrawComponent` (JUCE backend, `~:483-591` post-change) gained one behavioural addition: an `actionDispatch` callback + `acceptsClick_` flag, firing a Draw node's plain `action` on `mouseUp` when the release did not drag past the existing drag threshold and landed inside the component — needed because Draw nodes could dispatch drag/double-click but never a plain click, and the new app's Play/Stop icons and single-click encoder press (Change 2/3, tasks.md 10.2) need exactly that. The change is deliberately minimal and surgical (one constructor param, one `SetNode` param, one new `mouseUp` override, two call-site updates) and kept trivially upstreamable — no new abstraction, no unrelated refactor.

The submodule sits on a **local branch `froggers-fork`**, not a detached HEAD, with this change as its own commit on top of the `1940ddcb` pin — not on `main`. **This is a real blocker, stated plainly, not buried: the gitlink this repo records now references a commit that exists ONLY on that local branch, in this one working tree, until `froggers-fork` is pushed to a remote the gitlink's readers can reach.** Concretely, until pushed: (1) the D12 browser-publish pipeline cannot resolve `External/Sheaf` from a fresh clone or CI checkout; (2) `git submodule update` from any other clone of this repo fails to find the referenced commit; (3) anyone else checking out this repo gets a broken/empty submodule directory. This supersedes this decision's own "no file inside `External/Sheaf` is edited" framing above and D1a's parallel claim below — both predate the fork and are now historical for the pre-2026-07-27 state only.

### D1a — Out-of-tree launcher registration via Sheaf's `sheaf-patch` hook
**Choice:** register `FroggersApp` into the `sheaf-patch` launcher through the out-of-tree app-registration hook introduced at pin `1940ddcb`, rather than by editing anything inside the submodule.

**The hook, traced:** `Main.cpp` gains two `#ifdef SHEAF_PATCH_EXTRA_APP_TYPE` guards (both keyed on `SHEAF_PATCH_EXTRA_APP_TYPE` alone) that `#include SHEAF_PATCH_EXTRA_APP_HEADER` and push one extra registration built by `SHEAF_PATCH_EXTRA_APP_REGISTRAR`, binding `LaunchRegisteredApp<SHEAF_PATCH_EXTRA_APP_TYPE>`. The Makefile gains five variables, **all five mandatory together** (a hard `$(error)` fires on partial configuration): `EXTRA_APP_DIR`, `EXTRA_APP_HEADER`, `EXTRA_APP_TYPE`, `EXTRA_APP_REGISTRAR`, `EXTRA_APP_HEADERS`. Left unset, no `-DSHEAF_PATCH_EXTRA` reaches the compiler and the build is byte-identical to upstream (upstream-confirmed).

**Why the hook has this shape.** `LaunchRegisteredApp<App>` is a **private member template of `SheafPatchApplication`** (`apps/sheaf-patch/Main.cpp:77-89`) needing `window_` and `activeSession_`, so an external app cannot assemble a complete `SynthAppRegistration` on its own. The launcher supplies the launch binding; the app supplies only its type, manifest, and registrar. `include/synth/AppRegistry.hpp` is data structures only — there is no registry singleton and no discovery mechanism to plug into instead.

**`EXTRA_APP_HEADERS` is mandatory by design, not convenience.** It must list our own headers so edits to them trigger a rebuild. Upstream caught the trap this guards against: an `APP_HEADERS +=` placed before the `APP_HEADERS :=` assignment is silently clobbered, producing builds that succeed while silently ignoring changes to our headers.

**Invocation:**
```
make -C External/Sheaf/projects/synth/apps/sheaf-patch \
  EXTRA_APP_DIR=$PWD/app EXTRA_APP_HEADER=FroggersRegistration.hpp \
  EXTRA_APP_TYPE=synth_froggers::FroggersApp \
  EXTRA_APP_REGISTRAR=synth_froggers::MakeFroggersRegistration \
  EXTRA_APP_HEADERS="$(ls $PWD/app/*.hpp $PWD/app/dsp/*.hpp)"
```

**Corrected 2026-07-27:** the two-header example this decision previously showed was actively dangerous, not merely stale. The app has 18 headers; `APP_HEADERS` is a literal prerequisite list and no `-MMD` dependency files are generated, so the 14 unlisted headers (all of `app/dsp/`) were untracked and edits to them produced builds that succeeded while ignoring the change — precisely the trap this decision's own text warns about below. Use `app/build-launcher.sh`, which globs.

**Consequence: no file inside `External/Sheaf` is edited by this change.** True at `1940ddcb`; the hook itself is entirely upstream.

**RESOLVED 2026-07-27 (late) — the fork is gone and this claim holds again.** For part of 2026-07-27 the submodule sat on a local branch `froggers-fork` two commits ahead (`04818deb`, `7fa9ce34`, both in `projects/synth/juce/PortableJuceBackend.hpp`) adding plain-click dispatch for Draw nodes. Because those commits existed only on one machine, the gitlink was unresolvable from any other checkout and the browser publish was blocked. **The fork has been reverted**: the submodule is back on upstream pin `1940ddcb`, which is reachable on `origin/main` of `jvictor0/Sheaf`, so the gitlink resolves from any clone and publication is no longer blocked on this.

The app-side cost of reverting: encoder press and Play/Stop are **double-click**, not single click, because `Node::doubleClickAction` is the only action hook stock Sheaf dispatches for Draw nodes at this pin. See `app/FroggersUiSurface.hpp` `SetNodeAction`/`SetNodeActionAndLabel`. jvictor0 is expected to land plain-click support upstream; when it does, those two functions and the assertion in `app/FroggersSurfaceTests.cpp` flip back to `node.action`. The reverted work is preserved on the local `froggers-fork` branch for upstreaming.

### D1b — Build system is a Makefile, modelled on `apps/miniapp`; CMake rejected
**Choice:** the app builds with a Makefile, not CMake.
**Why:** Sheaf has no CMake anywhere — it is Makefile-only, its apps are header-only header sets, and `apps/braid-4` has no build target of its own (it is compiled into `sheaf-patch` and Sheaf's test binaries). The new app's Makefile is modelled on `apps/miniapp/Makefile` plus Sheaf's `runtime/juce_build.mk`.

**Alt rejected — `SYNTH_RUNTIME_MAIN`:** Sheaf's standalone-app precedent, `apps/miniapp/Main.cpp:11`, is deliberately **not** used. This app registers with the launcher (D1a) instead, so the existing requirement that Froggers defines no JUCE application entry point of its own still holds unchanged.

### D5 — Fixed 15-source modulation slate + Target/Back; drill-in to two levels
**Choice (REVISED, operator 2026-07-26).** The app registers **all 15 sources itself**; `StandardModulators` is **not used**. Order — external audio sits last, immediately before Target/Back, because those are the only sources that can go dead:

| Slot(s) | Source | Origin |
|---|---|---|
| 0-5 | **Random S&H 1–6** (Marbles-style) | Froggers (D8) |
| 6-8 | VCO 1 / 2 / 3 audio out | Froggers |
| 9-11 | VCO 1 / 2 / 3 envelope follower | Froggers |
| 12 | Noise | Sheaf `NoiseModulatorProcessor` (`include/synth/DspNoise.hpp:48-54`) |
| 13-14 | External audio — audio rate, envelope follower | Froggers |
| *(cell 15)* | Target / Back | fixed UI cell |

**Why `StandardModulators` drops out.** The operator asked for six Marbles-style S&Hs "customizing the StandardModulators that use the braid4 visualization." That is not possible: `kRandomCount = 4` is a hard `static constexpr` (`StandardModulators.hpp:27`) and the four visualizers are hardcoded members dispatched by a switch (`:46-49,188-191`) — `Configuration` lets you relocate and recolour the four, not change how many exist. Independently, `DspRandomLfo` has **no deja-vu or loop-length concept**, so its randoms could not be Marbles even at the right count. And with 0-5 taken by the six S&Hs and everything else assigned, there is **nowhere to put** `StandardModulators`' four randoms — the slate is full.

**What is still reused (this is not a rewrite of Sheaf's facilities):**
- `GangedRandomLfoVisualizer` is a standalone public template (`include/synth/GangedRandomLfoVisualizer.hpp:247-248`) — instantiable directly by the app, so Braid's random visualization is preserved without the aggregate.
- `NoiseWaveformVisualizer` (`include/synth/NoiseWaveformVisualizer.hpp:14`) and `NoiseModulatorProcessor` (`DspNoise.hpp:48-54`, constructible from a voice count alone) are likewise standalone.
- Registration itself is `Modulators::SetModulationSource` (`src/ParameterModulation.cpp:552-572`), the same call `StandardModulators::Register()` makes. **Registration order is load-bearing** — that function bounds-checks only and will silently overwrite a claimed index.
- `OpenModulationView` requires ≥16 encoders for 15 modulators (`:2818-2821`), which is exactly the grid size.

**Dropped with `StandardModulators`:** the four fixed-rate random walks (500 ms / 2 s / 6 s / 16 s) and the Constant modulator. Neither was ever chosen for Froggers — both arrived via `DefaultConfiguration()`.

**Drill-in (RESOLVED, operator 2026-07-25) — what Sheaf gives and what the app must add.** Sheaf provides *unlimited* depth and a Back that always exits fully; it has **no level model at all** (see the "No depth model" trace row). Specifically: `Bank`'s modulation state is one `Parameter* selected_` plus one bool; `Bank::HandlePress` opens a view for any non-null cell that isn't `selected_` (`:2647-2648`); `Deselect()` returns to the bank's parameter grid, not one level up; and `OpenModulationView` is **private** (`ParameterModulation.hpp:646`), so the app cannot re-enter a level it has left. Therefore:
- **Levels 1 and 2 come free** — pressing a top-level parameter opens the depth grid, and pressing a depth cell opens that depth parameter's own view. No app code needed.
- **The third level is refused app-side.** The app keeps its own level counter in the press routing and simply does not dispatch the press that would open level 3. This is the only added mechanism.
- **Back exits to the parameter grid from any level**, matching Sheaf's native `Deselect()`. A one-level pop is explicitly **not** implemented: it would require synthesizing a stack around a private API, and the operator has accepted full-exit instead.
**External-audio degradation (RESOLVED, operator 2026-07-25):** when no external input is available the two external-audio sources are marked **not connected**: present but inert, rendered as disconnected — never hidden. The slate is always 15 sources in the same order, so cell positions never shift with cabling.
- **Mechanism (RESOLVED, operator 2026-07-25): set `ModulatorMetadata::connected = false` when no external input is present.** `connected` *is* Sheaf's built-in "present but inert" flag, and it delivers every requirement at once — no bespoke affordance needed:
  - **Slate size is unchanged.** `OpenModulationView` pushes a cell for **every** modulator index regardless of `connected` (`src/ParameterModulation.cpp:2843-2852`); `EnsureModulationDepthParameter` returns `nullptr` for a disconnected source (`:2784-2786`) and the cell is pushed with `.parameter = nullptr` (`:2850`). 15 cells + Target/Back, positions fixed, whatever the cabling.
  - **Randomization skips them for free.** `Bank::RandomizeModulationDepths` selects eligible modulators **solely** by `source.connected` (`:2889,2898`).
  - **Rendering is inert natively.** A null cell yields a default `EncoderDrawState` (`EncoderDraw.hpp:306-364`, `return {}` at `:364`) with `connected == false`, which is the existing disconnected-encoder appearance. No desaturated-colour hack.
  - **Storage accounting stays consistent.** `MissingModulationDepthCount` also gates on `connected` (`:2805-2806`), so it does not budget slots for depth params that will never be allocated.
  - **Correction:** an earlier draft of this design claimed the sources must stay *connected* or the fixed-slate guarantee would break. That was wrong — see the corrected D9b note.

### D8 — Six Marbles-style Random S&H sources with no source-level controls, clocked by Sheaf's master clock
**Choice (REVISED, operator 2026-07-26):** six modulation sources at slots 0-5, labelled **"Random S&H 1"–"Random S&H 6"**, modelled on Mutable Instruments Marbles' **X** section — stepped random voltages with deja-vu looping over a stored loop, plus spread/bias/steps character. **One of the six (Random S&H 6) is a Y-style source**: a slow, smooth, full-range random clocked at a small fraction of the others' rate and **deliberately immune to deja-vu**, matching the real module's Y output. They are advanced on **transport quarter notes** via `block.clockPlan->TransportQuarterNotesAt(sample)` (`MasterClock.hpp:198`, plan nullable — `AppContext.hpp:84`); external MIDI clock sync comes free via `HandleExternalClock`/`SyncConfig` (`MasterClock.hpp:344-350,15`).

**Source #6's mechanism, resolved.** Three requirements collide: (a) advance on the quarter-note pulse, (b) smooth output, (c) reuse `GangedRandomLfoVisualizer` unmodified. They cannot all hold: `GangedRandomLfoVisualizer<N>` binds to a `GangedRandomLfoUiState<N>` (`include/synth/GangedRandomLfoVisualizer.hpp:247-251`) which is only produced by `GangedRandomLfo::Process(const GangedRandomLfoInput&)` (`include/synth/DspRandomLfo.hpp:311-325`) — a **per-sample, rate-driven** update (`m_roundElapsedSamples += 1.0` at `:322`) whose timing comes from `RandomTimingConfig{muSeconds, sigmaSeconds, internalSigmaHz}` (`:18-22`, resampled per round). There is no tick, trigger, or advance input.
**Resolution (preserves every operator decision):** source #6 is a `GangedRandomLfo` with `VoiceCount = 1`, made tempo-following by recomputing `muSeconds` each block from `block.clockPlan->QuarterNotesPerSample()` and the sample rate so one move spans 16 quarter notes (four bars). It is therefore tempo-**proportional**, not phase-locked to the quarter-note grid — which is correct for a "structural drift" source and is what makes the framework visualizer reusable unmodified. **Hazard:** `GangedRandomLfo::Process` calls `ValidateInput` on **every sample** and `ValidateRandomTimingConfig` **throws** `std::invalid_argument` (`DspRandomLfo.hpp:26-30`), so the tempo-derived seconds must be clamped finite and positive before reaching the audio thread.

**No source-level controls, no page (operator 2026-07-26).** To be precise about what "no controls" means: each source still has an ordinary **modulation depth** encoder per target parameter — bipolar, defaulting to neutral/off (`ModulationDepthConfig`, `src/ParameterModulation.cpp:1869-1870`). What it has no control over is its **own behaviour**. desktop-v2 **deleted** the Random S&H module page and its bag parameters — *Step chance / Deja vu / Bag size / Slew / Spread / Bias* — keeping Random S&H 1/2 as modulation lanes only (`desktop-v2/Source/V2DesktopPageDisplayNames.hpp:11-14`; the shared table still carries the page for web/v1 at `sim/V2ParamDisplayNames.hpp:28,36,45`). Of those, `src/core/Marbles.hpp` reads only **seven** knobs (`GetParam(0)..GetParam(6)` at `:81-87` = Step chance (shared), Deja vu 1, Bag size 1, Slew 1, Deja vu 2, Bag size 2, Slew 2) — **Spread and Bias are not among them**; those two are page rows the class never reads. That page is **not** recreated and no seventh bank is added. Each source carries a fixed character, and **all variation happens through the second modulation layer** — you drill into a source's depth cell and modulate it. This is precisely what the 2-level drill-in exists for: *"slew" is just modulating one of those Random S&Hs.* It is also why the depth cap is 2 and not 1.

**Consequence for the DSP port:** **`src/core/Marbles.hpp` is hardcoded to exactly two channels and is not a drop-in six-source unit.** `m_marbles[2][8]`, `m_filter[2]`, `m_size[2]`, `m_index[2]`, `m_dejaVuKnob[2]`, `m_output[2]`, and every loop is `for (i = 0; i < 2; ++i)`. Worse for independence: `m_probability` is a **single shared scalar**, not per-channel, and both channels share **one** `RGen m_rgen` instance rather than independent streams. `FroggersEngine` embeds one instance wired to fixed mod taps `m_modMgr.m_mods[5]`/`[6]`. Six independent sources therefore require either three instances (each seeded distinctly, or their loops will correlate) or generalizing the hardcoded 2 to a template/runtime count. Record the choice in packet 3; the fixed mod-tap wiring is dropped with the page coupling.

**Sanctioned divergence: `RGen` is made per-instance, not ported verbatim (packet 3 finding).** `src/core/RGen.hpp:12` declares `static uint32_t s_state;` (defined `inline` at `:66`) — the xorshift32 state is a **class-static**, not a member, so every `RGen` anywhere in the frozen codebase (both of Marbles' two channels included) reads and advances **one process-global stream**; the original Marbles' two lanes were never statistically independent. Five (soon six) independent Random S&H lanes require independent streams, so the port's `RGen` (`app/dsp/RandomShLane.hpp`) makes the xorshift32 state an ordinary per-instance member seeded in the constructor — same recurrence, same constants, different storage class. This is a deliberate, sanctioned divergence (D3: "copy if you want," not "copy byte-for-byte"), not a bug fix owed back upstream. **Consequence for parity testing:** because the frozen source's RNG is a shared global stream and the port's is per-instance and separately seeded, the two do not and cannot produce the same output sequence — RNG *output* is therefore not a valid parity target. Parity tests may only pin the **recurrence** (the xorshift32 formula itself, `NextUInt`/`UniGen`/`RangeGen`) and the **bag/deja-vu logic** (`Increment`/`Process`) against known inputs, never end-to-end RNG output against the frozen struct.

Also: **spread and bias are new DSP, not ported** — no range-narrowing or centring exists in `src/core/Marbles.hpp`, so D8a's "narrow, centred" character for #3 must be written, not copied. The copied Marbles keeps its bag/deja-vu core (`src/core/Marbles.hpp:83-144`) but sheds its `m_page->GetParam()` coupling entirely — no page pointer, no knob reads. Spread/bias/steps/loop-length become construction-time character per source rather than parameters.

### D8a — The six sources' fixed characters (PROVISIONAL, operator 2026-07-26)

Because there is no source-level control, these constants **are** the sound. The set is organised as a **subdivision ladder** across the three locked-loop sources, so their relationship is predictable rather than arbitrary:

| # | Rate | Loop | Period | Range | Character |
|---|---|---|---|---|---|
| 1 | ♩ | 8 | **2 bars** | full | long phrase, quarter pulse |
| 2 | ♪ | 8 | **1 bar** | full | eighth pulse, one-bar phrase |
| 3 | ♪ triplet | 8 | **⅔ bar** — realigns with the barline every 3 repetitions (2 bars) | narrow, centred | polyrhythmic triplet shimmer |
| 4 | ♩ | free | — | full, ~5 quantised levels | unpredictable stepped jumps |
| 5 | 1 bar | free | — | full, slewed | slow deliberate moves |
| 6 (Y) | 4 bars | deja-vu immune | — | full, smooth | structural drift |

**Clock conventions:**
- `MasterClock` supplies no bar or time signature (see the trace row), so this table defines **1 bar := 4 quarter notes (4/4)**. "Realigns with the barline" means realigns with the 4-QN grid. If a time signature is ever introduced, this table is re-derived.
- Per-source clock mechanism, stated once: #1 and #4 use `Phasor2Tick` with `multiplier = 1`; #2 `multiplier = 2`; #3 `multiplier = 3`; #5 needs a **division**, so it pre-scales `time` by ¼ with `multiplier = 1`; #6 is not tick-driven at all (see the #6 mechanism resolution above).

**Why this shape:** 1–3 are *memorable* (locked loops, so a patch develops a groove), 4–5 are *unpredictable* (fresh values, never settles), 6 is *structural* (slow enough to shape a section). #1→#2 is a halving; #3 breaks the halving on purpose.
- **#3 is deliberately polyrhythmic, not symmetric** (operator 2026-07-26). The 8-slot bag caps loops at 8, so a full bar of triplets (12 steps) is unavailable. A 6-step loop would repeat cleanly twice per bar; **8 steps was chosen instead** precisely because ⅔ of a bar drifts against the barline and resolves 3-against-2 every two bars.
- **#3 is the only narrow, centred source.** Every other one is full-range, which is hostile to pitch. Exactly one gentle source makes the set usable without a spread control.
- **Depth is bipolar** (`ModulationDepthConfig`, `src/ParameterModulation.cpp:1869-1870`), so all six are implicitly available inverted — 12 usable behaviours. None of the six is spent on polarity variety, and the sources can afford to be opinionated since nothing is imposed until a depth leaves neutral.

**Status: provisional.** Rate and loop structure are confident. **#4's ~5-level quantisation is the weakest choice** — it is a judgement about what makes the *set* useful, not something derived from Froggers or Marbles, and it is the most likely to be overruled on hearing. Validate the table by ear in packet 8 (task 8.6) before treating it as settled; changing it after patches exist shifts every patch.

**Visualizers — two kinds, both Braid-styled:**
- The five X-style sources get a **new** `Visualizer` rendering the remembered loop as a waveform with a playhead at the current index. Sheaf has nothing for this: `DspRandomLfo` has no loop concept and `GangedRandomLfoVisualizer` draws an *extrapolated future* path, not remembered history (`DspRandomLfo.hpp:172-182`; `GangedRandomLfoVisualizer.hpp:248`, drawing `:215-234`).
- The Y-style source is a smooth random walk, which is **exactly** what `GangedRandomLfoVisualizer` already draws — reuse it directly (it is a standalone public template, `:247-248`).

### D14 — Two randomize affordances: Randomize All and Randomize Page, both context-sensitive by view (operator, 2026-07-26; REFINED operator, 2026-07-26)
**Choice:** Froggers' four existing randomize affordances — two global (Randomize / Rand Mod) and two per-page (Randomize / Rand Mod) — are replaced by exactly **two**: **Randomize All** and **Randomize Page**. Both are **context-sensitive**: what each does depends on which view is currently displayed — a parameter page, a level-1 mod-detail grid, or a level-2 depth grid.

**The governing symmetry — this is the point of the design: "All" means wider and deeper; "Page" means exactly what is displayed.**

**Randomize All**, by view:
- Pressed on a **parameter page**: randomizes every top-level parameter's **value** across all six banks (**including** the six per-bank Crispy controls, **excluding** global Crunchy — Crunchy warps every parameter in every bank, so randomizing it would make every other randomized value unpredictable; it stays under manual control) plus all **level-1** modulation depths. It does **not** descend to level 2. Materialization ceiling stays 915 (793 when external audio is disconnected and only 13 sources are `connected`).
- Pressed on a **level-1 mod-detail grid**: randomizes that parameter's 15 depths **and materializes and randomizes their level-2 depths**. Scope is 15 + (15 × 15) = **240** parameters for that one focused parameter — not the 13,725 a global two-layer fan-out would force.
- Pressed at **level 2**: there is no deeper level (the cap is 2, D5), so Randomize All and Randomize Page **coincide** — both perform the single `Bank::RandomizeModulationDepths` call on that depth parameter's own 15 depths.

Mechanism throughout: the app selects the target set, **Sheaf performs every mutation** — values through `Modifier::Random` (`src/ParameterModulation.cpp:2872-2873`), depths through `Bank::RandomizeModulationDepths` (`:2881-2913`). The app implements no mutator of its own.

**Randomize Page** applies one uniform rule — randomize exactly what is displayed — unchanged by this refinement:
- a **parameter page** → that bank's nine parameter values (plus its Crispy, excluding Crunchy, by the same rule as Randomize All); **no depths**.
- a **level-1 mod-detail grid** → that parameter's 15 depths, a single `RandomizeModulationDepths` call.
- a **level-2 depth grid** → that depth parameter's own 15 depths, a single `RandomizeModulationDepths` call — identical to what Randomize All does at that level, per the coincidence noted above.

Level 2 is now reachable through **either** button: Randomize Page always reaches it (per its "exactly what is displayed" rule), and Randomize All reaches it **only** when pressed while an L1 grid is displayed — never from a parameter page.

**Why the *global* press stops at L1.** There are 61 top-level parameters (6 banks × 9, plus 6 per-bank Crispy, plus the one shared Crunchy). L1 depths are 61 × 15 = **915**; L2 depths would be 915 × 15 = **13,725**. Fanning the global (parameter-page) press across both layers would force the entire L2 matrix to materialize — the same ~13.7k allocation already flagged as follow-on C's VST3 blocker — and `Bank::EnsureModulationDepthParameter` would start returning `nullptr` once `CanAllocate()` fails (`:2790-2792`), producing a silently partial randomize. Capping the *global* press at L1 holds materialization at 915 (or 793 with external audio disconnected) and keeps follow-on C's lazy-allocation option open. This is why the global press stops at L1 — it is not a statement that Randomize All in general never reaches L2: the L1-grid press above does, deliberately, because its reach is bounded to exactly 240 parameters for one parameter rather than the full matrix.

**Why:** operator, 2026-07-26, refined 2026-07-26. Four affordances mapped onto Sheaf's mechanics one-to-one without adding musical value; two affordances, context-sensitive by view, remove nearly all app-side randomization logic while still reaching level 2 through two different, appropriately-scoped paths.

**Button placement reuses Froggers' existing homes (operator, 2026-07-26).** No new layout is invented. desktop-v2's global strip command band holds four buttons laid out left-to-right before the Crunchy label (`desktop-v2/Source/ui/GlobalStripV2.cpp:160-167`, constructed at `:30-36`), with labels from `sim/ParamDisplayNames.hpp:110-123`: "Rand All" (`RandAll`), "Rand Mods" (`RandMods`, tooltip "Randomize live mod depths" at `GlobalStripV2.cpp:63`), "Rand waveforms" (`RandWaveforms` → `m_host->RandomizeVcoMorphs()`, `:70`), and "Rand Resample" (`MarblesStep` → `m_host->PressButton(0)`, `:76`). Per-page randomize buttons do **not** currently exist: desktop-v2 removed them deliberately — `desktop-v2/Source/ui/SubmodulePagePanel.cpp:11-13` records "Per-page Randomize/Randmod header buttons removed (desktop-v2 'Randomization affordances are not duplicated'): global Rand All / Rand Mods in the command band are the single surface now." The new placement:

- **Randomize Page** goes in the per-page/bank header — deliberately **restoring** the position desktop-v2 removed. The reversal is sound because the reason for the original removal no longer holds: v2's per-page buttons duplicated the global ones one-to-one, whereas this pair have genuinely different scopes (whole-app vs. exactly-displayed), so the anti-duplication rationale does not apply to them.
- These are positions in the **ported layout** (D11), not JUCE reuse — the v2 design is ported while the v2 implementation stays frozen.

**Two retired buttons (operator, 2026-07-26).** The four-button command band becomes **one** global button (Randomize All) plus **one** per-page button (Randomize Page); the other two are retired, not ported:

The new app's Crunchy exclusion is recorded here as an intentional behavioral change, with that citation, precisely so nobody later "restores" v2's behavior as a regression fix.

**Consequence — three flagged QA judgement calls, not defects.** Randomize All on a parameter page applies Sheaf's per-call bias 61 times, so expect ~61 L1 depth changes per press in aggregate — bounded and cheap, but it may not read as "few"; if it feels like too much, the place to tighten is the app's **target-set selection** (touch a random subset of the 61 rather than all of them), **not** Sheaf's constant. A single `RandomizeModulationDepths` call is a no-op 50% of the time (see the trace row's bias table), so an individual Randomize Page press on a mod-detail grid is a visible no-op half the time. And whether Randomize All on an L1 grid reaching L2 (240 parameters materialized for one focused parameter) is musically desirable or too destructive is a third judgement call, distinct from the first two because it is the one path that creates L2 storage rather than just re-randomizing existing depths. All three are settled by ear in task 12.x, never by editing Sheaf's constant.

**Amends resolved decision 14** (see below): Sheaf remains the only randomization *mutator*; the app chooses the *target set*, the aggregate reach, and now the *view-dependent scope*. ### D17 — The master clock's transport quarter-note pulse gates the ASR; MIDI notes dropped (operator, 2026-07-27; REVISED 2026-07-27)

The operator's 2026-07-27 decision is that **the master clock's quarter-note transport pulse gates the envelope instead** — this works entirely within Sheaf today, needs no upstream change, and is implemented in this same change.

**Choice:** the ASR gate — `dsp::VcoAdsrState`, ported verbatim from `src/core/VcoAdsrState.hpp` (`setGate(bool)` at `:39`, the `m_gateHigh` flag at `:123`), which section 6a made audible only by pinning the gate permanently on (tasks.md §6a's "Discovered during implementation" note, now superseded) — is driven by the **master clock's transport quarter-note pulse**, read once per sample from `AudioBlock::clockPlan`, not by MIDI notes and not by any other note-like event.

**The in-Sheaf precedent is `apps/miniapp/MiniAppCore.hpp`'s own ADSR gate** (its clock-gate block spans `:322-329`; the guard is `:323-324`, the phase computation `:325-327`, and the duty-cycle assignment itself — `adsrGate = phase >= 0.0 && phase < 0.5` — is `:328`, not `:327`; an earlier reading of this citation as "`:323-327`" undercounted by one line and this document now cites the corrected range). It derives `phase` from `block.clockPlan->TransportQuarterNotesAt(absoluteOutputSample)` minus its own floor, guarded on `block.clockPlan != nullptr && block.clockPlan->TransportState() == synth::ClockTransportState::Running`, and gates open for the first half of every quarter note. **This app follows that exact idiom — same duty-cycle formula, same guard shape — and does not invent a different one.** The one deliberate deviation: miniapp calls the precondition-carrying `TransportQuarterNotesAt` (`MasterClock.hpp:198`, precondition `Contains(absoluteOutputSample)`, `:192-198`) after only a null/running check, which the design trace elsewhere in this document already flags as insufficient on its own; this app instead calls the containment-safe `TryTransportQuarterNotesAt` (`:200`, returning `std::optional<double>`) and treats an empty result as gate-closed, which is strictly safer and changes nothing about the audible duty cycle when the plan does contain the sample.

**Pitch stays entirely on the three VCO pitch knobs.** There is no transposition source of any kind now that MIDI notes are out of the picture, so the previous draft's transposition law — multiplying each VCO's knob-set frequency by `2^((note − 60) / 12)`, MIDI 60/middle C as the unity reference — is **dropped, not deferred**. Nothing in this app computes or applies that factor; the three pitch knobs are the sole pitch authority, exactly as topology spec `froggers-vco-topology` already requires independent of this decision.

**Consequence, stated plainly.** The app is **silent while the transport is stopped** and pulses open/closed at the tempo (first half of every quarter note gated open, second half closed) while the transport runs. This supersedes section 6a's "a freshly started app should make sound with no user input" expectation outright — a freshly started, never-transported app is silent by design, not a regression. See tasks.md §6a's amendment and revised §6b.

**MIDI-note support is not abandoned as a concept, only decoupled from this decision.** If Sheaf gains a real note-delivery mechanism upstream in the future, note-driven gating could be revisited as a separate, later change — but this decision does not depend on that ever happening, and nothing here is written to anticipate it.

**Non-goal unaffected.** The existing non-goal "MIDI mapping/profile redesign; polyphony" (Goals/Non-Goals) remains untouched by either the original or this revised D17 — neither one is a redesign of Sheaf's controller-mapping/profile system (`MidiControllerSlot`/`MidiProfileKind`/encoder-CC mapping).

**Status: IMPLEMENTED (2026-07-27)** — see tasks.md §6b (revised) and §6a's test updates.

**Verified absence (retained from the original D17 for the record — this is *why* the choice above exists, not a live blocker anymore).** Sheaf ships **no note-delivery mechanism** to any app: `include/synth/AppContext.hpp`'s `midiBus` (`:95`) and `instrument`/`defaultInstrument` (`:101-102`) fields carry no raw-note/pitch/gate field of any kind; `include/synth/AppConcepts.hpp`'s only optional application hooks are `HasPrepareToPlay`/`HasProcessFrame` — no MIDI hook exists to detect; `MessageIn::Type` (`include/synth/ParameterModulation.hpp:930-949`) enumerates `ParamIncDec, ParamSetAbsolute, ParamPush, ToggleReset, ToggleRandom, ToggleRandomMod, ToggleGestureSelect, SetGestureSelect, SelectParamBank, Start, Continue, Stop, Clock, SetGestureValue, SceneSelect, SetSceneBlend, GridPress, GridRelease, GridPressureChange, SelectGrid, NextParamBank, PrevParamBank` — no note, pitch, or gate member exists; and every note-consuming `MidiInProcessor` in `src/MidiController.cpp` maps a note strictly onto a **pre-configured** control-surface target: `EncoderMidiInProcessor::Process` treats a note as a CC-like encoder push (`:725-731`), `SystemButtonMidiInProcessor::Process` maps a note to a pre-configured system-button press/release (`:881-903`), `PolyphonicPressureMidiInProcessor::Process` maps a note+pressure to a pre-configured target its own config validator restricts to `GridPressureChange` only (`:851-871`, rejected at construction otherwise, `:823-824`). `apps/braid-4/Braid4Core.hpp:196` and `apps/miniapp/MiniAppCore.hpp:256` are the only MIDI-touching lines in either reference app, and both only install `synth::DefaultMidiInstrumentConfig()` (a control-surface profile), never reading a note. **No note-on/off-with-pitch event reaches `SynthApplication::Init`/`ProcessBlock` anywhere in Sheaf.** This is not an oversight: Sheaf is a **control-surface framework for knob-driven instruments** — its entire MIDI pipeline (`MidiControllerSlot` → `CreateMidiControllerProfile` → `midiBus_` → `ParameterManager`) maps hardware encoders/buttons/pads onto parameters, which is exactly why `braid-4` and `miniapp`, Sheaf's own reference apps, are themselves note-less. Recorded here at length so nobody re-proposes MIDI notes for this app's gate without first knowing this trace exists.

**Historical record — the original choice this section replaces, quoted verbatim, superseded in full above:**

> MIDI note-on/off events drive both halves of the currently-untriggered ASR path. The app is monophonic (`numVoices = 1`, D4) — there is one shared gate, not one per note. A small held-note stack resolves overlapping notes by last-note priority: the most recently pressed held note governs gate and pitch; releasing it while another note is still held falls back to that note; the gate goes low only when the stack empties. Every new note-on retriggers the envelope into `Stage::Attack` (multi-trigger, not true legato). A held note transposes all three Audio-bank VCOs together by multiplying each VCO's already-knob-set frequency by `2^((note − 60) / 12)`, MIDI 60/middle C as unity, preserving the pitch knobs' intervals exactly.

No code was ever written against this original choice — the design was superseded at the same operator turn it would otherwise have unblocked, once the verified-absence trace above was in hand.

## Risks / Trade-offs

- **[DSP fork]** Copied DSP diverges from `src/core/` over time → Mitigation: parity unit tests at copy time; divergence is intentional and recorded (D3). Note the parity reference for fuegoize is the **firmware's** `src/core/Parameter.hpp:143`, not `sim/Fuegoize.hpp` (D6).
- **[Character change]** Fuego row re-indexing changes the sound at identical settings (D6) → Mitigation: explicit operator acceptance, recorded as resolved; no legacy row-id fallback is offered.
- **[Two Sheaf copies]** Submodule + frozen vendored slice at `desktop-v2/External/Sheaf` (a plain vendored directory — `.gitmodules` lists only `External/theallelectricsmartgrid` and `External/Sheaf`) → Mitigation: since the build is a Makefile (D1b), not CMake, the guard is a build- or test-time check that no include path the new target resolves against reaches into `desktop-v2/External/Sheaf` — e.g. asserting the compiler's effective include search path (or grepping the Makefile's `-I` flags) contains no `desktop-v2/External/Sheaf` entry (task 1.3).
- **[Upstream drift]** Sheaf moves under us → Mitigation: submodule pin; deliberate bumps only.
- **[Browser toolchain]** Emscripten/ABI surface is exacting → Mitigation: mirror `build-browser-apps.mjs` flags exactly; validate with Sheaf's own `validate-deployed-catalog.mjs`.
- **[Mono unproven]** The whole parameter model assumes `numVoices = 1` behaves identically to N>1 through parameter → modulation → encoder draw, which Sheaf does not demonstrate → Mitigation: task 2.5 validates it end-to-end in packet 2, before any bank or slate work depends on it. If mono turns out to be second-class, that is a stop-and-ask, not a workaround.
- **[Modulator index drift]** `Modulators::SetModulationSource` (`src/ParameterModulation.cpp:552-572`) bounds-checks only and has no reservation registry, so it will silently overwrite a claimed index — registration order is load-bearing and the test must assert all 15 slots **by identity, not by count** (task 6.2/6.6).
- **[Marbles is 2-channel]** `src/core/Marbles.hpp` is hardcoded to two channels with a shared RNG and a shared probability scalar → six independent sources is a restructure, not a copy (D8). Mitigation: decide instances-vs-generalization in packet 3; assert per-source loop independence in task 8.4.
- **[Shared Crunchy unproven]** One `Parameter` in six banks is expressible but undemonstrated in Sheaf (D5a) → Mitigation: validate alongside the mono check before packet 5, stop-and-ask if second-class.
- **[Scope]** This is an app-layer rewrite → Mitigation: greenfield against a working reference app (`braid-4`), packetized, each packet independently green.
- **[Randomize All aggregate reach]** Sheaf's per-call bias applied 61 times (Randomize All on a parameter page) yields ~61 L1 depth changes per press, which may not match the intended "few" → Mitigation is app-side target-set selection, settled by ear in packet 12, never by editing Sheaf's constant (D14). Separately, Randomize All pressed on an **L1 mod-detail grid** materializes 240 parameters (that parameter's 15 depths plus their 225 level-2 depths) for one focused parameter — bounded, but it is the **one path in the whole design that creates L2 storage**, so `Bank::EnsureModulationDepthParameter`'s `CanAllocate()` failure (`:2790-2792`) must surface as a detectable partial randomize on this path, not truncate silently (D14, task 6.8).
- **[Permanent publisher identity]** `publisher.id` = `daguilarc` is chosen once and cannot be changed after publication — saved patches are addressed at `patches/<publisher-id>/<app-id>`, so a later change orphans every user's saved patches → Mitigation: `daguilarc` is fixed now (D12), before any patch can exist under it; every other identity field (`publisher.name`, `displayName`, `author`, `category`) stays changeable.
- **[Browser tooling prerequisites]** Two facts the plan initially omitted: Sheaf's browser tooling is TypeScript and ships unbuilt (`browser/dist/src/*.mjs` does not exist until compiled), and `browser/dist` is not gitignored, so packaging output lands as files inside the Sheaf submodule's working tree → Mitigation: compile Sheaf's browser tooling as an explicit first pipeline step (D12), and clean or exclude `browser/dist` build artifacts after packaging so the frozen-tree/scope verification (only `pages.yml` changes outside the new app tree) still holds.
