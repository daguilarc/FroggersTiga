## App-supplied MIDI catalog: an app offers the Controllers page its own actions, device layouts and mappings

Stacks on #12 (`browser-audio-activation`); the diff against that branch is this change alone.

### What changed, and why

The Controllers page offered one fixed list of mappable targets, `UISystemMessageCatalog()`: the library's parameter-modulation vocabulary plus the sample app's device defaults. An app with its own named actions (randomize, reset, bank and scene selection, transport, tempo) and its own controllers had no way to offer them, and a bus `ParamPush` opened the library's modulation view rather than the app's own drill-in.

An app may now declare a `MidiCatalog()` (`HasMidiCatalog`, `include/synth/MidiAppCatalog.hpp`). The catalog is data, read once at engine construction:

- **actions**: `ui::Action` names the app's surface already routes, each with a value and a label; an action with an `analogRange` is driven by an analog control and receives `min + v * (max - min)`.
- **libraryKinds**: which library message kinds the page still offers.
- **encoderPressAction**: when set, a `ParamPush` on either bus is forwarded to the app as that action with the position as its value, instead of the library's `HandlePress`.
- **patchCarriesMappings**: patch files carry `midiInstrument` at schema version 2 (see Persistence).
- **deviceDefaults**: complete controller layouts the page offers per controller row.

Dispatch keeps the audio thread free of app calls: `MessageInBus::Apply` pushes `AppAction` / `AppEncoderPress` onto `ParameterMessageOutBus` (the ring `MessageThreadTick` already drains), and the tick dispatches `ui::Action`s to `app.PortableSurface()` on the message thread. So an app action or a forwarded encoder press lands within one message-thread tick (`uiFrameHz`, 30 by default) plus one audio block, not in the block the MIDI arrived in. That is a view-level latency, the same one an on-screen click has; a knob turn still reaches `ParameterManager` in its own block, as before. The out-bus holds 64 messages, so a full fader sweep between two ticks (about 33 CCs) fits; a burst larger than that drops the excess.

Two message kinds are appended (`AppAction`, `HoldDrill`); every existing ordinal holds. **Hold Drill** lives in the profile's input chain: while a button mapped to it is held, a knob turn pushes one `ParamPush` for that knob and its value does not move; release makes it a plain knob again.

**Presets.** The add row gets a Preset combo: the app's device defaults followed by a Custom entry per device kind. Choosing a preset and pressing Add installs that default's config through a wizard with an empty form and commits it. The new row keeps that preset's identity (`wizardId`) for as long as the row exists; editing its mappings no longer clears that identity or reverts anything to Custom. When a row's `wizardId` still resolves and its config has diverged from what that preset currently generates, a Restore button appears on the row; pressing it reinstalls the preset's mappings without touching the row's name, ports, or disposition. The static `ControllerWizardRegistry()` becomes `MakeControllerWizardRegistry(catalog)` (app defaults when supplied, else the library's Twister descriptor), and the per-row Reconfigure action is removed; the discovered-device configure flow stays.

**Persistence, two policies side by side.** An association or analog mapping for an app action persists `appAction` and `appActionValue`; the runtime index is resolved against the catalog on a copy of each controller config at every rebuild. An action the catalog does not know drops that one row from the copy with one log line; the saved config keeps it. `ParseMessageType` still fails a whole runtime config closed on an unknown message *type*, as before.

**Connect-time SysEx.** `MidiControllerProfileConfig::openSysEx` is a list of messages an output processor sends exactly once after every output `Reset()` (open or reopen). Any device that needs a mode message on connect can use it.

**Patch files.** Only when the app's catalog sets `patchCarriesMappings`: `BuildPatchJSON(..., carryInstrument)` writes schema version 2 with a `midiInstrument` section, `LoadPatchJSON` hands a loaded section back to the caller, and the engine applies it on the message thread through `EditInstrument`. Every other app writes and reads version 1 exactly as today; a version-2 file's section is ignored for an app without the flag.

**Controller row fits its host.** The controller header is two 36 px lines instead of one: identity (disclosure, name, device display name) on line one, ports and lifecycle on line two — a status dot immediately before each port's combo, the combos captioned "MIDI in" and "MIDI out", then Delete and, on a row created from a preset whose mappings have diverged from it, Restore, and, on a row created from a preset the registry still resolves once both its ports are bound, Release. The rename field moves off the header entirely: it is the expanded editor's first row, a field captioned "Name" beside a Rename button. The header's minimum width holds at 724 px, well under a 900-wide host's content and down from the previous 1240. The row's device label and the add row's selector show `MidiProfileKindDisplayName` (WRLD.Bldr, MF Twister, Launchpad, Generic) while the persisted config keeps the profile-kind token; the add row is captioned "Preset", offering the app's presets then one Custom entry per kind, and pressing Add with nothing chosen adds the preset the combo displays. An added row takes its preset's name (numbered when that name is taken) and binds its ports to a connected device matching the preset, otherwise "(none)". One legend ahead of the first row names the three status colours, sharing its dot width with the rows'.

**A rename keeps the row open.** `MidiConfigViewModel` keys expand state and section presentations by controller name, and `Rebuild` erases entries whose name is no longer in the instrument, so a rename came back collapsed — and with the Name field now inside the editor, that collapse was the field's own outcome. `NoteControllerRenamed(from, to)` moves both caches with the name, called on the rename success path before the refresh rebuilds. A same-name re-add after a delete still starts fully collapsed. A blacklisted row has no expanded editor and so no Rename; reclaim it before renaming it.

**Test dependency lists are generated, not written.** The five test binaries whose translation units reach `ControllersPageUI.hpp` carried hand-written header prerequisites, and the browser contract test's list omitted that header — a page change left it stale and passing. Those rules now compile with `-MMD -MP` and `-include` the generated depfiles. The browser contract rule is split so its two translation units each get one: a single compiler invocation over two sources writes one depfile recording only the last of them, which would have silently dropped the test unit's own headers.

In the browser backend a combo box's `<select>` and a text field's `<input>` now fill their node's box and a select clips its text (sprs-18), where before they sized to their content and overlapped their neighbours. A new `FitsWithinViolations(tree, bounds)` criterion folds each node's origin over its ancestor chain and reports any rectangle outside the page's content bounds; the Controllers fixture asserts it empty at 900 by 620 for a Twister, a Generic, a Launchpad and a Blacklisted row, collapsed and then through every open state (each section, a row added in each group that accepts one). The row's reworked controls are held to that criterion headlessly rather than by screenshot: the fixture now covers 24 states, including a row offering Restore and one not, a row offering Release and rows withholding it for each of its two reasons, a released row, and Launchpad rows collapsed and expanded. The browser render at 1000 by 820 quoted earlier was measured against the previous row layout and has not been repeated for this one.

### What does not change for an app without a catalog

The offered message list, the Twister wizard, patch files at version 1, and every message kind. The add row's Preset combo does appear for every app (offering the library's Twister preset plus a Custom entry per kind), and the per-row Reconfigure action is gone for every app.

### Testing

Unit suites cover each mechanism (engine dispatch, forwarding, catalog resolution and the drop-one-row rule, JSON round trips, Hold Drill sequences, `openSysEx` once-per-reset, the add row's Preset combo, wizard-identity persistence, and Restore, the registry, patch schema 1 and 2 both ways, and the rename that keeps its row and sections open); the JUCE-backed Controllers page simulation runs green; the miniapp and braid-4 suites are unchanged. The fits-within fixture asserts no violations at the page's own 900 by 620 content bounds, and carries a deliberate positive control at 600 px that reports 17 — so a run of zeros means the criterion is live rather than silent. The depfile split is proven by a two-leg control: touching `ControllersPageUI.hpp` rebuilds the browser contract test where the previous Makefile reported it up to date, and touching a header only its own translation unit reaches rebuilds it too. The standalone controllers harness app is removed; nothing invoked it, and its inbound references go with it. The Pages workflow now runs `browser/tests/ui-backend.spec.ts` (the select-fills-wrapper assertion) against the built bundle.

To try it by hand with the app that consumes it (frogg3rs `main`, `daguilarc/frogg3rs`): open the Controllers page, add a Generic controller, map a button to Randomize All, and press it; add a MIDI Fighter Twister preset row, edit one of its mappings, watch Restore appear on the row, press it, and watch the factory mapping return; open a row's editor and rename it from the Name field, and the editor stays open on the same row; save a patch, change a mapping, reload the patch; map a button to Hold Drill, hold it and turn a knob.

**UNCONFIRMED on hardware:** the Akai APC40 mkII (Ableton) layout sends the protocol's mode-introduction SysEx on connect; no unit was available while writing this, and it stays unconfirmed until one is. The Launchpad presets prove the `openSysEx` path on hardware you have — no interface writes that field by hand, so the check is run through the presets themselves, not by editing a profile directly: add a Launchpad from the add row by picking your model (Launchpad X, Launchpad Pro MK3, or Launchpad Mini MK3) and connect it; its output should switch the pad into programmer mode once, not again on the next tick, with every pad going dark. Testing by the upstream author is ideal.
